# 08 同步：手机与电脑之间

> 状态：**第一版，引擎已实现**（2026-10-31，M7；实现说明见 §13）。决策 S1–S7 见 §1，已经用户确认：端到端加密暂时不做，其余按评审建议。排在 M7；M1 只需要数据层的约定（§9）。
> 相关：数据约定 [`01` 约定、§9](01-database.md#9-约束与迁移)（R11）；手机端 [`00` §3.13](00-concept-design.md#313-手机端d8)；接口 [`06` 的 sync 组](06-interface.md)。
> 原型：[设置 → 数据 → 同步](../prototypes/settings.html#data)、[手机版 我 › 同步](../prototypes/mobile.html)。

## 1. 决策

| # | 决定 | 说明 |
|---|---|---|
| **S1** | **共享文件夹 + 变更文件**，不搭我们自己的服务器 | 符合 R12（不做托管）。每台设备把自己的改动写成文件放进一个共享文件夹，其他设备读来合并 |
| **S2** | 后端先做 **iCloud Drive** 和 **WebDAV**（坚果云、Nextcloud、群晖等）；局域网直连以后再做 | 首发人群多用 Mac + iPhone，iCloud 零配置；WebDAV 覆盖 Windows、Android 和不用 iCloud 的人。两种后端用同一套文件格式 |
| **S3** | **暂不做端到端加密** | 文件只压缩不加密，传输由 iCloud / HTTPS 保护；云盘服务商理论上能读到内容，设置页开启同步时说明这一点。文件头留 `enc` 字段，以后加密不用改格式 |
| **S4** | 合并按**字段**比较，后改的赢；时间用混合逻辑时钟（HLC） | 两端改了同一条记录的不同字段，两个改动都保留；设备时钟差几分钟也不会判错。细则见 §4 |
| **S5** | 复习卡片不同步状态，合并复习记录后**按时间顺序重算** | 两端离线各复习过同一张卡也不会丢记录 |
| **S6** | 导入的原始文件（PDF、EPUB、图片）**默认同步**，可关 | 关掉后只同步解析后的正文与结构，原文件只在导入它的设备上 |
| **S7** | 同步**默认关**，在设置里开启；每台设备只写自己的文件夹 | 不依赖 iCloud / WebDAV 处理并发写冲突（它们这方面都很弱） |

## 2. 文件夹布局

```
Tibi Sync/                         iCloud：应用容器 Documents/ 下，"文件"App 里可见；WebDAV：用户填的路径
  library.json                     资料库标识：{ library_id, format: 1, created_at, created_by }
  devices/
    <device_id>.json               设备信息：名称、平台、应用版本、最后上线、已读到各设备的哪一批（acks）
  changes/
    <device_id>/
      base-0000000120.jsonl.gz     压缩后的基线（§6）
      0000000121.jsonl.gz          一批改动，序号递增、不回头改
      0000000122.jsonl.gz
  blobs/
    ab/ab3f…e9                     原始文件与图片，按 SHA-256 命名，内容相同只存一份
```

- 一台设备只写 `devices/<自己>.json`、`changes/<自己>/` 和它导入的 `blobs/`；`library.json` 只在新建资料库时写一次。所以不存在两台设备写同一个文件。
- `device_id` 是首次开启同步时生成的 UUIDv7，存在本机 `sync_state`；重装应用算新设备。

## 3. 变更文件格式

每个文件是 gzip 压缩的 JSON Lines。第一行是批次头，后面每行一条改动：

```jsonc
{"v":1,"enc":null,"device":"0193…","seq":122,"from":"1793450000000-0-a1","to":"1793450420000-3-a1","n":3}
{"op":"put","t":"terms","id":"0193…","f":{"meaning":"最终结果","status":3},"c":{"meaning":"1793450100000-0-a1","status":"1793450100000-1-a1"},"src":{"status":"user"}}
{"op":"add","t":"review_logs","row":{"id":"0193…","card_id":"0193…","rating":3,"reviewed_at":1793450300000}}
{"op":"del","t":"memories","id":"0193…","c":"1793450420000-3-a1"}
```

| op | 用于 | 内容 |
|---|---|---|
| `put` | 普通表的新建与修改 | 只带改过的字段 `f`，以及每个字段的时钟 `c`；熟练度这类有来源的字段另带 `src` |
| `add` | 只追加的表：`review_logs`、`term_status_log`、`learning_events`、`practice_logs` | 整行 |
| `del` | 删除（墓碑） | 只有表名、ID、时钟，**不带内容** |

**HLC**：字符串 `<毫秒>-<计数>-<设备短号>`，按字典序可比较。本机每次写入取 `max(本机时钟, 见过的最大 HLC) + 1`，读到别的设备的改动时也推进自己的时钟。这样即使手机时间慢了 5 分钟，它之后做的改动仍然排在它看到的改动后面。

## 4. 合并规则

拉取时按设备、按批次顺序读，逐条应用：

| 数据 | 规则 |
|---|---|
| 一般字段（释义、笔记、标签、标题、设置项） | **按字段**比较时钟，大的赢；本机在 `sync_clocks` 里记着每个字段最后一次改动的时钟 |
| 熟练度（`terms.status`） | 也是时钟大的赢，但**系统自动推断的改动不覆盖用户亲手做的**：来源是 `auto_*` 的改动，只有在对方的值也是自动推断时才生效 |
| 只追加的表 | 按 `id` 去重后全部保留 |
| 复习卡片排期（`cards` 的 FSRS 字段） | 不比较两端状态。应用完一批改动后，对涉及到的卡片取全部 `review_logs`，按 `reviewed_at` 排序，用 FSRS 从头重算。暂停、指定题型这类手动字段照一般字段处理 |
| 阅读进度 | 时钟大的赢（最后在哪台设备上读，就以哪台为准） |
| 派生数据：遇见次数、`daily_stats`、全文索引 | 不同步，合并后在本地重算 |
| 删除 | 删除的时钟大于该行任何字段的时钟时，整行删掉；之后到达的、时钟更早的修改丢弃。删除之后又改了的（时钟更大）按"改的赢"恢复这一行 |

**重复的同一条**：UUID 不会冲突，但两台设备可能各自建了"同一个"东西。按自然键认作一条：

| 表 | 自然键 |
|---|---|
| `terms` | `(kind, text)` |
| `documents` | `content_hash` |
| `tags` | `name` |
| `conversations`（`kind = day`） | `day` |

两条中 **ID 较小（更早建的）留下**，另一条的字段按上面的规则并进来，引用它的记录改指向留下的那条，并在 `sync_aliases` 记一笔（以后收到指向旧 ID 的改动时自动转过去）。两台设备按同一规则选，结果一致。

## 5. 推送与拉取

**推送**：Core 的每次写入（领域服务的仓储层统一处理）在同一个事务里：推进 HLC、更新 `sync_clocks`、往 `sync_outbox` 追加一条。推送时把 outbox 里的改动打成一批，写到 `changes/<自己>/<seq>.jsonl.gz`，成功后清掉这些行。一批最多 2,000 条或 1 MB。

**拉取**：读 `devices/` 下其他设备的信息，对每台设备列出比 `sync_peers.last_read_seq` 新的批次，按序号下载并应用（§4），一批应用完就更新游标。最后把自己读到的位置写进 `devices/<自己>.json` 的 `acks`。

**什么时候同步**：

- 应用启动、回到前台、退到后台前；
- 一轮复习结束、导入完成、读完一篇；
- 应用开着时每 5 分钟；
- 设置或手机"我 › 同步"里的"立即同步"；
- iCloud：系统通知文件夹有变化时（`NSMetadataQuery`）也拉一次；WebDAV 只按上面的时机检查，不轮询得更勤（坚果云等服务对请求频率有限制）。

小组件读主应用写在 App Group 里的快照（J7），不自己同步。

## 6. 压缩与墓碑

- 每台设备只压缩**自己**的文件夹：当所有已知设备的 `acks` 都读过自己的第 N 批，就把 `base` 和第 N 批之前的文件合成一份新的 `base-N`：每个字段只留最后的值，被删掉的行只留墓碑，不留内容；然后删除旧文件。
- 墓碑在所有设备都读过后，从本机库里真正删除（硬删）。对话、记忆这类要求硬删的内容，压缩后云端也不再留有正文（S3 不加密，这一步是唯一的清理手段，所以压缩在每次同步后检查）。
- 超过 90 天没上线的设备不再计入"所有设备"，压缩和墓碑不等它；它回来时按新设备处理：先读全部 `base` 和之后的批次，再推送自己没推出去的改动。设置里也能手动移除设备。

## 7. 不同步的内容

| 内容 | 原因 |
|---|---|
| API Key、WebDAV 密码 | 留在每台设备的钥匙串里，各自填写 |
| 设备自己的设置：深浅色、窗口大小、正文字号、托盘行为 | 每台设备习惯不同。学习相关的设置（每日目标、新词上限、目标记得率）同步 |
| 进行到一半的复习会话（`review_sessions`） | 在另一台设备上从头开始一轮；已经答过的已写进 `review_logs`，不会重复计分 |
| 写操作审计与撤销（`skill_audit`）、任务的步骤（`job_steps`）、用量明细 | 只对本机有意义；任务和用量的汇总随对话、设置同步 |
| 词典、全文索引、语音缓存、`daily_stats` | 可以在本地重新生成 |

## 8. 后端

**iCloud Drive**（macOS、iOS）

- 应用的 iCloud 容器 `iCloud.app.tibi`，文件放在容器的 `Documents/Tibi Sync/` 下，所以在"文件"App 里可见、可备份。
- Tauri 没有现成插件，需要写一个 Swift 小插件：取容器路径、`startDownloadingUbiquitousItem` 触发下载未下到本地的文件、`NSMetadataQuery` 监听变化。iCloud 不保证多快送达，界面只显示"上次同步时间"，不承诺实时。
- 用户没登录 iCloud 或关了 iCloud Drive 时，提示去系统设置打开，或改用 WebDAV。
- Windows 上的 iCloud 客户端第一版不支持，Windows 用户用 WebDAV。

**WebDAV**（所有平台）

- 用户填地址、账号、应用密码（坚果云在"账户信息 → 安全选项"里生成），密码存钥匙串。"测试连接"会建一个测试文件再删掉。
- 只用 `PROPFIND`、`GET`、`PUT`、`MKCOL`、`DELETE`；每次同步先 `PROPFIND` 列目录，只下载新批次。
- 只接受 `https://`，局域网地址（如群晖）可以用 `http://`，但要用户确认一次。

## 9. 对 M0 / M1 的要求

同步在 M7 做，但下面几条现在就要遵守，否则到时要迁移数据：

1. 主键 UUIDv7、外键 TEXT（R11，已写进 01）。
2. 所有写入经过 Core 的仓储层，不在别处直接写 SQL，这样 M7 能在一处加上 HLC、`sync_clocks` 和 outbox。
3. 删除一律先写 `deleted_at` 墓碑。
4. 只追加的表不做 `UPDATE`。
5. 派生数据（遇见次数、每日汇总）能从原始数据重算。

开启同步时，本机已有的数据全部当作一批初始改动推送（字段时钟取各行的 `updated_at`），所以 M1 不需要 outbox 和 `sync_clocks`。

## 10. 界面

**电脑：设置 → 数据 → 同步**（默认关）

- 关闭时：一句说明 + "开启同步"。
- 开启流程：选后端（iCloud Drive / WebDAV）→ WebDAV 填地址、账号、应用密码，测试连接 → 如果文件夹里已有 Tibi 资料库，显示"已有 2 台设备 · 上次更新 10 分钟前"，点"加入"；没有就"新建资料库"。加入时本机已有的数据会合并进去，不会覆盖。
- 开启后：状态行（"已同步 · 2 分钟前" / "正在同步…" / 失败原因 + "重试"）、"立即同步"、设备列表（名称、平台、最后上线，可移除其他设备）、"同步导入的原始文件"开关、"停止同步"（本机数据保留，云端文件不删）。
- 开启时说明一次："同步文件不加密，存放在你选的云盘里。"

**手机：我 › 同步**：同样的内容放在一个底部面板里；后端在 iPhone 上默认 iCloud Drive。

**出错时**（两句话，按 03 §9）：

| 情况 | 文案 |
|---|---|
| 网络不通 | 没连上网络。恢复后会自动同步。 |
| WebDAV 账号或密码错 | WebDAV 登录失败。检查账号和应用密码。 |
| iCloud 没登录 | 这台设备没有登录 iCloud。去系统设置登录，或改用 WebDAV。 |
| 云盘空间不足 | 云盘空间不够了。可以关掉"同步导入的原始文件"。 |
| 别的设备用的是新版本的格式 | 另一台设备的 Tibi 版本更新。升级后才能继续同步。 |

## 11. 验证

M7 开工时先写一组自动化场景测试（两到三个模拟设备 + 一个本地文件夹后端）：

- 两端离线各改同一个词的不同字段、同一字段；
- 两端离线各复习同一张卡，合并后排期与单机按时间顺序复习的结果一致；
- 两端各导入同一篇文章、各建同一个生词；
- 一端删除、另一端修改；
- 设备时钟相差 ±10 分钟；
- 一批文件只上传了一半（应用中途退出）；
- 一台设备 90 天不上线后回来；
- 压缩后新设备加入。

## 13. 实现说明（M7，2026-10-31）

代码在 `packages/core/src/sync/`，场景测试 `packages/core/test/sync/scenarios.test.ts`（§11 里除了"90 天不上线"和"压缩后加入"都有，这两条等压缩做了再加）。和上面设计不同或补充的地方：

- **改动怎么记**：不在仓储层逐个加，而是开启同步时给每张同步表建 SQLite 触发器，写进 `sync_outbox`（T27）。所有写入都会被记下，以后加的写操作也不会漏。哪些表、哪些字段同步见 `sync/spec.ts`：FSRS 排期字段、本机文件路径、遇见次数不同步；`providers`、`jobs`、`job_steps`、`skill_audit`、`usage_records`、`review_sessions`、`daily_stats`、`audio_cache` 整表不同步；设置里 `tts.*`、`mcp.*`、`backup.*`、`sync.*`、`onboarding.*` 是本机的。
- **时钟**：一条 put 的字段共用一个时钟（推送时按改动发生的本机时间分配，保持先后）；读的时候也认每个字段一个时钟的写法。
- **熟练度**：用户亲手标的总覆盖系统自动推断的，自动推断的不覆盖用户的；两边同类才比时钟。这样结果不受同步先后影响。
- **重复的文章**：留下的那份保留自己的章节和句子，输掉那份的章节、句子丢掉（`sync_aliases.to_id = ''`），引用它们的语境句子置空（语境里另存了原句文字），生词、阅读记录等改指留下的那份。
- **复习卡片**：拉取后对涉及到的卡片按 `review_logs_valid` 的时间顺序用 FSRS 从头重算；卡片按 `term_id` 认作同一张。
- **半截的批次**：先写批次文件、再更新设备文件里的 `head`，别人只读到 `head` 为止；文件夹后端写临时文件再改名。
- **后端**：除了 iCloud Drive 和 WebDAV，多了"文件夹"（任意本地文件夹：Dropbox、OneDrive、NAS 挂载等），桌面之间也能同步。Mac 上的 iCloud 用应用容器 `iCloud~app~tibi`，需要签名并带 iCloud 权限的版本；iPhone 上的 Swift 插件还没写（M7-4）。
- **自动同步**：启动后 10 秒、每 5 分钟、本机改动后 30 秒（合并连续改动）。
- **还没做**：压缩与墓碑清理（§6）、原始文件（blobs，S6）、删除之后又改了的整行恢复（现在 `deleted_at` 当普通字段合并）。
